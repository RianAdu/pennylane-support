# Decisions

Every choice between real alternatives, with what was rejected and why. Scope, roles and data scale were left open on purpose by the hiring team, so these decisions are part of the assessment. Requirements live in `docs/requirements.md`; agent rules in `AGENTS.md`.

**Adding a decision:** append a row with the next ID. If a decision is reversed, don't delete the row; add a new one and note the change under History.

## Decision log

| # | Area | Decision | Rejected | Why |
| --- | --- | --- | --- | --- |
| <a id="d1"></a>D1 | Primary user | Learner-first community; the admin moderates on the same screens | Staff triage inbox; separate learner and staff areas | The brief says the platform "enables learners to seek help, share knowledge". One set of screens fits the time. |
| <a id="d2"></a>D2 | Roles | Two viewer roles: learner and admin. Mentor, staff and support stay as badges on posts | Four roles from the data; single mock user; fake login | The brief names learners and an admin. Extra roles cluttered every screen. Permissions live in one table, so a moderator role later is one new row, not new screens. |
| <a id="d3"></a>D3 | Navigation | A labelled left sidebar: Community with its 13 categories, then Challenges, plus Insights for the admin | Challenge-first navigation; top tabs; an icon-only rail | The brief makes support the primary focus, so threads are home. Every challenge card leads into its threads. Categories become a browsing path, as on the real forum, and labels keep navigation accessible. |
| <a id="d4"></a>D4 | Design reference | Content model from the PennyLane forum and challenges page; design inspiration for layout patterns from the PennyLane forum and various online forums | Copying an existing layout; a generic admin dashboard | The data mirrors both real products. Today help and challenges live on separate sites; connecting them is the improvement. |
| <a id="d5"></a>D5 | Data scale | Server-style API: the mock server filters, sorts and paginates | Load everything, filter in the browser | The brief asks for "larger datasets". The UI only ever holds one page, so it scales unchanged. |
| <a id="d6"></a>D6 | Framework | Vite + React + TypeScript | Next.js App Router | A client-side app against mocked APIs gains nothing from server rendering. MUI needs extra setup in the App Router, so the simpler stack wins. Next.js stays the right choice for content pages like pennylane.ai. |
| <a id="d7"></a>D7 | Mock API | Mock Service Worker (MSW) | Next.js Route Handlers; importing JSON directly | Mocks live in frontend code, as the brief asks. The app makes real `fetch` calls, so a real backend replaces only the mock. The same handlers run in tests. Importing JSON directly would hide how a server behaves. |
| <a id="d8"></a>D8 | Server state | TanStack Query | `useEffect` plus state; Redux | Caching, loading and error states, keeping the previous page while the next loads, refetching after a change. |
| <a id="d9"></a>D9 | URL state | Search, filters and page in URL search params (React Router) | Component state; a global store | Views are shareable and bookmarkable, and the back button works. |
| <a id="d10"></a>D10 | Client state | React context for the current role only | Zustand, Redux | Only one piece of global client state exists, and every screen depends on it, so a full re-render on change is correct. Components use a useRole() hook, so moving to Zustand later changes one file. In production the role comes from the session and becomes server state. |
| <a id="d11"></a>D11 | UI library | MUI with a custom theme | Tailwind | Accessible components out of the box: focus handling, ARIA, keyboard support. The theme acts as design tokens. |
| <a id="d12"></a>D12 | Charts | MUI X Charts (free version) | Recharts, D3 | Uses the same theme as the rest of the UI, so less styling work. |
| <a id="d13"></a>D13 | Markdown | `react-markdown`, raw HTML disabled | `dangerouslySetInnerHTML` | Descriptions are Markdown. Not rendering raw HTML closes the XSS door. |
| <a id="d14"></a>D14 | Data changes | Pending state, then refetch | Optimistic updates | These are moderation actions the server can refuse (403, 409). Optimistic updates would show a change and then undo it, and need rollback code for the list and detail caches. A short pending state is honest and simpler. Optimistic updates fit high-frequency, low-risk actions like upvotes, which are out of scope. |
| <a id="d15"></a>D15 | Testing | Vitest + Testing Library, MSW in tests, one Playwright run | Jest, Cypress | Vite-native, and the mock server is reused across all test layers. |
| <a id="d16"></a>D16 | Data normalization | Normalize once when the mock store loads; raw JSON never edited; every rule unit-tested | Editing the JSON; fixing data in components | The data has deliberate inconsistencies (see requirements, Data findings). Fixing them in one tested place keeps components simple and makes the rules reviewable. |
| <a id="d17"></a>D17 | List tabs | Intent tabs: Latest, Unanswered, Solved (+ Needs attention for admin); other filters behind "More filters" | A status dropdown and a full filter bar | Tabs match what a learner wants ("has someone solved this?"); four statuses in a dropdown expose the data model, not the user's intent. |
| <a id="d18"></a>D18 | Thread layout | Answer-first: Q:/A: markers, accepted answer directly under the question, "N people have this question too" | Plain chronological forum thread | A learner arrives to find the answer. Putting it second, not buried in replies, is the one bold design idea. |
| <a id="d19"></a>D19 | Votes | Display only (opening post's upvotes, helpful counts) | Working upvotes | Voting is a new data change with its own rules; out of scope for a proof of concept. Listed under What's next. |
| <a id="d20"></a>D20 | Theme | Light theme; Atkinson Hyperlegible for UI, JetBrains Mono for code | Dark theme first | Long threads read best on light; the font supports the accessibility story. MUI makes dark mode cheap later. |
| <a id="d21"></a>D21 | Mobile navigation | Below 900 px the sidebar becomes a temporary MUI Drawer behind a menu button | A dropdown menu | 15+ items would make a long scrolling dropdown. The Drawer shares one component with the desktop sidebar and gives focus trap, Esc and focus return for free. |
| <a id="d22"></a>D22 | Agent instructions | `AGENTS.md` holds all rules; `CLAUDE.md` imports it with `@AGENTS.md` | Rules only in `CLAUDE.md` | The reviewers may use any coding agent. `AGENTS.md` is the cross-tool convention; Claude Code reads `CLAUDE.md`, which imports it, so there is one source of truth. |

## History

How the plan changed during planning (Oct 6–7, 2026), and why. Useful context for anyone wondering why the obvious option wasn't taken.

| Date | Change | Reason |
| --- | --- | --- |
| Oct 6 | Next.js App Router → Vite + React (D6) | Considered Next.js with Route Handlers as the mock API. Rejected: no SSR benefit for a client app on mocked data, and extra MUI setup in the App Router. |
| Oct 6 | Route Handlers → MSW (D7) | MSW keeps mocks in frontend code, as the brief asks, and the same handlers run in Vitest and Playwright. |
| Oct 6 | Tailwind → MUI (D11) | Accessible components out of the box: focus handling, ARIA, keyboard support. |
| Oct 6 | Filtering moved from browser to mock server (D5) | The brief mentions larger datasets; the UI should never hold more than one page. |
| Oct 6 | Four viewer roles (learner, mentor, staff, admin) → two (D2) | The first wireframes showed every extra role added controls to every screen without a story the brief asks for. Mentor/staff/support became post badges. |
| Oct 6 | Top tabs → labelled left sidebar (D3) | Categories are the real forum's browsing path; labels beat icons for accessibility. |
| Oct 7 | Redrew list and thread wireframes (D4, D17, D18) | First versions looked like an admin console: dense tables, status dropdown, every field visible. Rebuilt around one user job per screen, with layout patterns inspired by the PennyLane forum and various online forums. |
| Oct 7 | Status dropdown → intent tabs (D17) | Learners think "unanswered" or "solved", not in five statuses. |
| Oct 7 | Vote box restyled as a tinted block (D19) | The bordered box read as a button while votes are display only. |
| Oct 7 | Sidebar on every page; thread page collapses it (D3) | Challenges and Insights needed the same navigation; the thread needs width for reading, the breadcrumb keeps the place. |
| Oct 7 | Responsive rules and phone wireframes added (D21) | Defined the 900 px drawer breakpoint and one-column layouts; only list and thread change structure on phones. |
| Oct 7 | "Show the ID next to the title" dropped | Titles repeat (723 of 800), but internal IDs mean nothing to learners. Rows are distinguished by excerpt, challenge and date; code keys on `identifier`. |
| Oct 7 | `CLAUDE.md` → `AGENTS.md` + import (D22) | Reviewers may use a different coding agent. |
| Oct 8 | Planning review before any code (D23–D34) | Reading the three documents against the wireframes and the data turned up 28 gaps and conflicts. Each was resolved in the documents first, so every slice and test can cite a written rule. |
| Oct 8 | D17 corrected: "five statuses" → "four statuses" | The data has four: open, answered, resolved, closed. |
| Oct 8 | `sort` removed from URL state and the API contract (D9, D27) | No screen has a sort control, and the parameter's values were never defined. |
| Oct 8 | Open chip: action blue → the waiting colour (D25) | The wireframe drew Open in the colour used for links and buttons. |
| Oct 8 | Demo learner `you` → an existing learner from the data (D29) | No user `you` exists in the data, so "own threads" could only be shown through the ask form, which is on the cut list. |
| Oct 8 | Description metadata stripped at normalization (D31) | Found while sampling list rows: descriptions restate status and priority, which search would expose to learners. |
| Oct 9 | Remaining work prioritized into three screen slices and a pass (D53); D17, D28 and D29 changed | The support system is the primary focus, so controls that repeat a pattern already demonstrated (another filter, another admin action, another chart) move to What's next, and the effort goes into the quality of the core screens. Moved: More filters (D17, with the challenge picker of D28), the learner's own-thread actions and their demo learner (D29), four of the five admin actions, related threads, the challenge page, the difficulty filter and two charts. |
| Oct 9 | Wireframes as structure only; production-quality visual design (D54) | This is a frontend role, so I chose to give visual design and UX real weight: wireframes define structure, and the visual design is held to production quality. |
| Oct 9 | Community list restyled and fixed in review (D56, D61, D63) | The first build of the list was structurally right and read as a wireframe with real data, so the visual layer was redone in three layers with the circuit motif. Review in the browser also found: the skip link stopped under the sticky top bar; a new page of the list left the viewer at the bottom; `main` took focus without showing it; the search field was cut to four letters at 375 px; row rules ran wider than the header; MUI's Chip could not be removed with a real button; action blue as a focus ring did not show on ink. Each is fixed, and the rule behind it is in the decision named. |
| Oct 9 | Insights built: a ruled strip of figures, a ranked list and one chart with a table (D69) | "Where learners struggle" was drawn as a chart; as a list every figure is text and every row is a link to the questions it counts. The monthly chart gained a "Show as table" in review, so its values do not depend on seeing the bars. |
| Oct 9 | `GET /api/challenges` returns challenges grouped by category instead of a paged list (D70) | The page shows every category as one row of cards. A paged list would cut a row in two, and the browser would have to group and count, which is the server's job (D5). |
| Oct 8 | Opening post: earliest timestamp → `post_id` 1 (D35) | The documented rule was wrong, and so was the sentence "`created_at` matches the earliest post". The data check run before the domain slice caught it: 220 conversations have a reply dated before the question. "Solved by the asker" went from 48 threads (an effect of the wrong rule) to 20, decided by author. |
| Oct 9 | Thread rail at 900–1199 px: below the thread → the strip (D64) | Under the thread the challenge's context sat below the reply form, where nobody reading the question sees it. The strip keeps it beside the question at every width below 1200 px, and the page has two layouts instead of three. |
