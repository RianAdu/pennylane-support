# Decisions

Every choice between real alternatives, with what was rejected and why. Scope, roles and data scale were left open on purpose by the hiring team, so these decisions are part of the assessment. Requirements live in `docs/requirements.md`; agent rules in `AGENTS.md`.

**Adding a decision:** append a row with the next ID. If a decision is reversed, don't delete the row; add a new one and note the change under History.

## Decision log

| # | Area | Decision | Rejected | Why |
| --- | --- | --- | --- | --- |
| D1 | Primary user | Learner-first community; the admin moderates on the same screens | Staff triage inbox; separate learner and staff areas | The brief says the platform "enables learners to seek help, share knowledge". One set of screens fits the time. |
| D2 | Roles | Two viewer roles: learner and admin. Mentor, staff and support stay as badges on posts | Four roles from the data; single mock user; fake login | The brief names learners and an admin. Extra roles cluttered every screen. Permissions live in one table, so a moderator role later is one new row, not new screens. |
| D3 | Navigation | A labelled left sidebar: Community with its 13 categories, then Challenges, plus Insights for the admin | Challenge-first navigation; top tabs; an icon-only rail | The brief makes support the primary focus, so threads are home. Every challenge card leads into its threads. Categories become a browsing path, as on the real forum, and labels keep navigation accessible. |
| D4 | Design reference | Content model from the PennyLane forum and challenges page; design inspiration for layout patterns from the PennyLane forum and various online forums | Copying an existing layout; a generic admin dashboard | The data mirrors both real products. Today help and challenges live on separate sites; connecting them is the improvement. |
| D5 | Data scale | Server-style API: the mock server filters, sorts and paginates | Load everything, filter in the browser | The brief asks for "larger datasets". The UI only ever holds one page, so it scales unchanged. |
| D6 | Framework | Vite + React + TypeScript | Next.js App Router | A client-side app against mocked APIs gains nothing from server rendering. MUI needs extra setup in the App Router, so the simpler stack wins. Next.js stays the right choice for content pages like pennylane.ai. |
| D7 | Mock API | Mock Service Worker (MSW) | Next.js Route Handlers; importing JSON directly | Mocks live in frontend code, as the brief asks. The app makes real `fetch` calls, so a real backend replaces only the mock. The same handlers run in tests. Importing JSON directly would hide how a server behaves. |
| D8 | Server state | TanStack Query | `useEffect` plus state; Redux | Caching, loading and error states, keeping the previous page while the next loads, refetching after a change. |
| D9 | URL state | Search, filters and page in URL search params (React Router) | Component state; a global store | Views are shareable and bookmarkable, and the back button works. |
| D10 | Client state | React context for the current role only | Zustand, Redux | Only one piece of global client state exists, and every screen depends on it, so a full re-render on change is correct. Components use a useRole() hook, so moving to Zustand later changes one file. In production the role comes from the session and becomes server state. |
| D11 | UI library | MUI with a custom theme | Tailwind | Accessible components out of the box: focus handling, ARIA, keyboard support. The theme acts as design tokens. |
| D12 | Charts | MUI X Charts (free version) | Recharts, D3 | Uses the same theme as the rest of the UI, so less styling work. |
| D13 | Markdown | `react-markdown`, raw HTML disabled | `dangerouslySetInnerHTML` | Descriptions are Markdown. Not rendering raw HTML closes the XSS door. |
| D14 | Data changes | Pending state, then refetch | Optimistic updates | These are moderation actions the server can refuse (403, 409). Optimistic updates would show a change and then undo it, and need rollback code for the list and detail caches. A short pending state is honest and simpler. Optimistic updates fit high-frequency, low-risk actions like upvotes, which are out of scope. |
| D15 | Testing | Vitest + Testing Library, MSW in tests, one Playwright run | Jest, Cypress | Vite-native, and the mock server is reused across all test layers. |
| D16 | Data normalization | Normalize once when the mock store loads; raw JSON never edited; every rule unit-tested | Editing the JSON; fixing data in components | The data has deliberate inconsistencies (see requirements, Data findings). Fixing them in one tested place keeps components simple and makes the rules reviewable. |
| D17 | List tabs | Intent tabs: Latest, Unanswered, Solved (+ Needs attention for admin); other filters behind "More filters" | A status dropdown and a full filter bar | Tabs match what a learner wants ("has someone solved this?"); four statuses in a dropdown expose the data model, not the user's intent. |
| D18 | Thread layout | Answer-first: Q:/A: markers, accepted answer directly under the question, "N people have this question too" | Plain chronological forum thread | A learner arrives to find the answer. Putting it second, not buried in replies, is the one bold design idea. |
| D19 | Votes | Display only (opening post's upvotes, helpful counts) | Working upvotes | Voting is a new data change with its own rules; out of scope for a proof of concept. Listed under What's next. |
| D20 | Theme | Light theme; Atkinson Hyperlegible for UI, JetBrains Mono for code | Dark theme first | Long threads read best on light; the font supports the accessibility story. MUI makes dark mode cheap later. |
| D21 | Mobile navigation | Below 900 px the sidebar becomes a temporary MUI Drawer behind a menu button | A dropdown menu | 15+ items would make a long scrolling dropdown. The Drawer shares one component with the desktop sidebar and gives focus trap, Esc and focus return for free. |
| D22 | Agent instructions | `AGENTS.md` holds all rules; `CLAUDE.md` imports it with `@AGENTS.md` | Rules only in `CLAUDE.md` | The reviewers may use any coding agent. `AGENTS.md` is the cross-tool convention; Claude Code reads `CLAUDE.md`, which imports it, so there is one source of truth. |

## History

How the plan changed during planning (Oct 6–7, 2026), and why. Useful context for anyone wondering why the obvious option wasn't taken.

| Date | Change | Reason |
| --- | --- | --- |
| Oct 6 | Next.js App Router → Vite + React (D6) | Considered Next.js with Route Handlers as the mock API. Rejected: no SSR benefit for a client app on mocked data, and extra MUI setup in the App Router. |
| Oct 6 | Route Handlers → MSW (D7) | MSW keeps mocks in frontend code, as the brief asks, and the same handlers run in Vitest and Playwright. |
| Oct 6 | Tailwind → MUI (D11) | Accessible components out of the box: focus handling, ARIA, keyboard support. |
| Oct 6 | Filtering moved from browser to mock server (D5) | The brief mentions larger datasets; the UI should never hold more than one page. |
| Oct 6 | Four viewer roles (learner, mentor, staff, admin) → two (D2) | The first wireframes showed every extra role added controls to every screen without a story the brief asks for. Mentor/staff/support became post badges. |
| Oct 6 | Top tabs → labelled left sidebar (D3) | Categories are the real forum's browsing path; labels beat icons for accessibility. |
| Oct 7 | Redrew list and thread wireframes (D4, D17, D18) | First versions looked like an admin console: dense tables, status dropdown, every field visible. Rebuilt around one user job per screen, with layout patterns inspired by the PennyLane forum and various online forums. |
| Oct 7 | Status dropdown → intent tabs (D17) | Learners think "unanswered" or "solved", not in five statuses. |
| Oct 7 | Vote box restyled as a tinted block (D19) | The bordered box read as a button while votes are display only. |
| Oct 7 | Sidebar on every page; thread page collapses it (D3) | Challenges and Insights needed the same navigation; the thread needs width for reading, the breadcrumb keeps the place. |
| Oct 7 | Responsive rules and phone wireframes added (D21) | Defined the 900 px drawer breakpoint and one-column layouts; only list and thread change structure on phones. |
| Oct 7 | "Show the ID next to the title" dropped | Titles repeat (723 of 800), but internal IDs mean nothing to learners. Rows are distinguished by excerpt, challenge and date; code keys on `identifier`. |
| Oct 7 | `CLAUDE.md` → `AGENTS.md` + import (D22) | Reviewers may use a different coding agent. |
| Oct 8 | Planning review before any code (D23–D34) | Reading the three documents against the wireframes and the data turned up 28 gaps and conflicts. Each was resolved in the documents first, so every slice and test can cite a written rule. |
| Oct 8 | D17 corrected: "five statuses" → "four statuses" | The data has four: open, answered, resolved, closed. |
| Oct 8 | `sort` removed from URL state and the API contract (D9, D27) | No screen has a sort control, and the parameter's values were never defined. |
| Oct 8 | Open chip: action blue → the waiting colour (D25) | The wireframe drew Open in the colour used for links and buttons. |
| Oct 8 | Demo learner `you` → an existing learner from the data (D29) | No user `you` exists in the data, so "own threads" could only be shown through the ask form, which is on the cut list. |
| Oct 8 | Description metadata stripped at normalization (D31) | Found while sampling list rows: descriptions restate status and priority, which search would expose to learners. |
| Oct 8 | Opening post: earliest timestamp → `post_id` 1 (D35) | The documented rule was wrong, and so was the sentence "`created_at` matches the earliest post". The data check run before the domain slice caught it: 220 conversations have a reply dated before the question. "Solved by the asker" went from 48 threads (an effect of the wrong rule) to 20, decided by author. |

## Added during the build

| # | Area | Decision | Rejected | Why |
| --- | --- | --- | --- | --- |
| D23 | Tab definitions | Unanswered = status open (128 threads). Solved = status resolved (294), with a check when the thread also has an accepted answer (169) | Unanswered as "no replies" (57) or "no accepted answer" (443); Solved as "has an accepted answer" (357) or "resolved or closed" (425) | Each tab then agrees with the chip on its rows and with the Insights tile "Open conversations". "No replies" includes resolved and closed threads; "has an accepted answer" would put Answered and Closed chips under Solved and leave out 125 resolved threads. |
| D24 | List excerpt | The opening post's content, cut at a word boundary at 200 characters with an ellipsis. Markdown stripping and the description fallback are deferred until new questions can be posted | The description; a Markdown stripper and a description fallback now | The opening post is the question in the asker's words. Descriptions vary in shape and carry headings and record metadata (D31). All 800 opening posts are plain text and none is empty, so a stripper or a fallback would be code that cannot run yet; a naive stripper would also damage `2*pi / (2**(k+1))` in one real post. |
| D25 | Status colours | Open = waiting, Answered = neutral grey, Resolved = solved, Closed = grey outline. Action blue is never used for status | Open in action blue, as first drawn | Blue means "you can click this". A status chip is not a control, and the waiting colour says what an open thread is: waiting for an answer. |
| D26 | Dependencies | Approved beyond the original stack list: `@emotion/react`, `@emotion/styled`, `@mui/icons-material`, `@testing-library/user-event`, `@testing-library/jest-dom`, `typescript-eslint`, `@vitejs/plugin-react`, `eslint-plugin-react-hooks` | Inline SVG icons; `fireEvent` and plain matchers in tests | The emotion packages are MUI's required peers and the rest is build and lint tooling. MUI's icons match the component library; `user-event` drives components the way a person does, which is what the component tests claim to cover. |
| D27 | List order | Latest activity only: no `sort` parameter, no sort control, and pinned threads keep their place | A `sort` parameter with a control; pinned threads first | No screen asks for another order, and each extra order multiplies the states to test. "Latest" should mean latest; pin stays a flag shown on the thread. |
| D28 | Challenge filter | M1 honours `challengeId` from the URL and shows it as a removable chip; the picker arrives in M2 on `GET /api/challenges` | Adding all 120 challenges to `/api/meta`; pulling the challenges handler into M1 | `pageSize` is capped at 50, so no M1 endpoint can list 120 challenges. Putting them in meta would change the contract and send a full list to the browser, against D5. The filter is mostly reached from a challenge card or an Insights link, which the chip covers. |
| D29 | Demo learner | One existing learner from the data, fixed in the mock server; chosen in M2 from learners with an open thread that has replies | A new user `you` who owns only threads created through the ask form | "Own thread" actions (FR-12) must be demonstrable without the ask form, which is on the cut list. |
| D30 | Role switcher placement | In the top bar at 900 px and wider, inside the drawer below that. The drawer lists all 13 categories | The top bar at every width; a collapsed "7 more categories" row in the drawer | At 375 px the top bar has room for the menu button, the brand and search only. The drawer scrolls, so hiding seven categories saves nothing and costs a tap. |
| D31 | Description metadata | Normalization strips the lines and table rows in descriptions that restate status, priority, category, topic, tags or an internal ID (status and priority in 333 descriptions, an ID in 521) | Rendering descriptions as they are; filtering at display time | Priority is admin only, and search reads the description on the server: a learner searching "urgent" would get exactly the urgent threads. A display-time filter does not cover search, and the embedded status goes stale once a thread's status changes. One tested place, as in D16. |
| D32 | Thread page navigation | Sidebar hidden; the top bar's menu button opens it as the same drawer used on phones; the breadcrumb keeps the place | Breadcrumb only; a narrow icon rail | The thread needs the width for reading, but the breadcrumb alone leaves no route to Challenges or Insights. Reusing the drawer adds no new component. |
| D33 | Top-bar search | Always searches questions and opens the Community list with the query | Search that changes target with the page ("Search challenges" on Challenges) | One box with one meaning, and the support system is the primary focus. |
| D34 | Challenge search | Cut: the Challenges page has a difficulty filter and no search. Listed under What's next | A second search field on the Challenges page; a top-bar search that switches target (D33) | The top bar searches questions everywhere, so challenge search would need its own field, states and tests on a secondary screen. 102 published challenges in 12 category rows are browsable with the difficulty filter alone. |
| D35 | Opening post | The opening post is `post_id` 1; replies are ordered by timestamp, then `post_id`. `created_at` is kept as given. "Solved by the asker" means the accepted answer's author is the asker (20 threads) | The earliest post by timestamp as the opening post, as first documented | `created_at` equals `post_id` 1's timestamp in 800 of 800 conversations, all 740 descriptions quote `post_id` 1, and all 357 accepted answers are mentor, staff or support posts. The timestamp rule made a reply the question in 220 threads and put "Solved by the asker" on 48 helper posts. The cost: those 220 threads show a reply dated before the question. |
| D36 | Internal IDs in prose | A challenge ID typed by the asker in a post stays (10 conversations; 9 descriptions quote it) | Removing the ID from post content and descriptions | Normalization removes metadata the system added, not words a learner wrote. Rewriting prose needs a rule per sentence shape and can break the sentence. |
| D37 | Code style | Function expressions for every function; `type` over `interface`; tests in a `__tests__` folder beside the code; test names in plain words without requirement IDs or printf placeholders. Enforced by ESLint | Leaving declarations and interfaces to taste; test files beside the source file; requirement IDs in test names | One way to write each thing keeps diffs about behaviour and makes agent-written code read like hand-written code. A lint rule holds a convention where a written one drifts. IDs in test names went stale when requirements moved; the commit message already carries them. |
| D38 | Test scope | Tests cover necessary behaviour: one test per distinct way the code can break, plus invariants checked over all 800 normalized conversations. Documented counts are not pinned in tests, with one exception: `mocks/queries/__tests__/realData.test.ts` runs the list and meta queries on the loaded data and pins the Unanswered (128), Solved (294) and Needs attention (47) totals and the 13 categories covering 800 threads. This narrows D16's "every rule unit-tested" to the rules that change data | A test per documented count; tests for values that are only passed through | A count test fails when the data changes, not when the code breaks, and a pass-through test repeats what the types already hold. 23 tests that each name one failure are easier to read and defend than 54. The counts stay in the requirements, checked against the files on Oct 8. The pinned totals are the exception because they check a tab's definition against the real data (D23, FR-7), which a fixture cannot: a wrong predicate that passes on three fixture rows fails on 800. |
| D39 | Roles and the query functions | The functions in `mocks/queries/` know nothing about roles. The handler calls `can()`, answers 403 for the Needs attention tab, drops `priority` and `assignee` for a learner, and passes a flag (`includeTriage`, `includeAssignees`) that says whether the response carries the admin-only fields | Passing the role into each query function | `can()` stays the only place a role is read, and each query is tested with plain inputs. A learner's list item has no `priority` or `assignee` key at all, which a test holds. |
| D40 | Unassigned filter | `assignee=unassigned` matches threads with no assignee | An empty value; a separate `unassigned=true` parameter | One parameter for one menu. No assignee in the data has that name. |
| D41 | Unknown filter values | An enumerated or numeric parameter that is not valid (`tab`, `priority`, `page`, `pageSize`) falls back to its default. An unknown `category`, `tag`, `challengeId` or `assignee` matches nothing and returns an empty list | Checking free values against the store and ignoring unknown ones | Ignoring an unknown category would show every thread under the wrong header. The parser stays pure and needs no store. |
| D42 | HTTP contract types | The response shapes (`ConversationSummary`, `Paged`, `Meta`, the tab names) live in `src/api/contract.ts`; the mock server imports them | Keeping them in `domain/types.ts` | They describe what crosses `/api`, not the domain. The mock implements the contract as a real backend would, and `domain/` stays free of API shapes. |
